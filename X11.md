# X11 Protocol Contract

This document records LWM's current ICCCM, EWMH, and LWM-specific behavior. It is the
source of truth for external X11 integration. Internal state and transition ownership
belong in [ARCHITECTURE.md](ARCHITECTURE.md).

## Window-manager ownership

LWM selects `SubstructureRedirectMask`, acquires `WM_S0`, refuses to start when another
window manager owns the screen, and broadcasts `MANAGER`. The window that owns `WM_S0`
is also the `_NET_SUPPORTING_WM_CHECK` window and is named `lwm`.

## Desktops and root properties

Each monitor has its own workspace set. LWM exposes that model as one flat,
monitor-major EWMH desktop list:

```text
desktop = monitor_index * workspaces_per_monitor + workspace_index
```

`_NET_CURRENT_DESKTOP` represents the focused monitor's current workspace. Sticky
windows use `_NET_WM_DESKTOP = 0xFFFFFFFF` and are visible across the owning monitor's
workspaces.

LWM maintains these root properties:

- `_NET_SUPPORTED`, `_NET_SUPPORTING_WM_CHECK`
- `_NET_CLIENT_LIST`, `_NET_CLIENT_LIST_STACKING`
- `_NET_NUMBER_OF_DESKTOPS`, `_NET_DESKTOP_NAMES`
- `_NET_CURRENT_DESKTOP`, `_NET_DESKTOP_GEOMETRY`, `_NET_DESKTOP_VIEWPORT`
- `_NET_ACTIVE_WINDOW`, `_NET_WORKAREA`

The client lists include normal clients, docks, and desktops, even when hidden.
`_NET_CLIENT_LIST` follows registration order. Cold adoption registers the managed
scene in QueryTree order, interleaving clients, docks and desktops; popups take no rank.
Across restart, surviving identities keep their saved ranks and newcomers follow the
entire saved range in observation order. Placement and transient dependencies do not
reorder registration. `_NET_CLIENT_LIST_STACKING` is
bottom-to-top. Hidden clients precede visible ones. Visible tiers are Below, Normal,
Above, and Fullscreen; desktops are Below and docks Above. Within a tier, floating
clients follow tiles, the active window is raised within its kind, then registration
order and ID break ties.

Visible floating transients follow visible managed parents even across tiers.
Missing or hidden parents impose no constraint. In a transient cycle, the parent
edge of the lowest base-ranked member is ignored; hints are not rewritten.

## Classification

LWM uses the first recognized atom in `_NET_WM_WINDOW_TYPE`:

| Type | Treatment |
| --- | --- |
| `DESKTOP` | managed in the Below tier, skipped by focus/taskbar/pager |
| `DOCK` | managed in the Above tier, strut-reserving, skipped by normal focus/taskbar/pager |
| `DIALOG` | managed floating |
| `TOOLBAR`, `MENU`, `SPLASH` | managed floating, skipped by taskbar/pager |
| `UTILITY` | managed floating, above, skipped by taskbar/pager |
| `NORMAL` or unknown | managed tiled; managed floating when transient |
| `DROPDOWN_MENU`, `POPUP_MENU`, `TOOLTIP`, `NOTIFICATION`, `COMBO`, `DND` | mapped directly, otherwise unmanaged |

Classification supplies defaults, not permanent constraints. A transient defaults to
skipping taskbar/pager. Type/transient updates change defaults on existing normal
clients; explicit floating/tiled, layer, or skip preferences survive. Runtime conversion
into desktop, dock, or direct-mapped popup behavior is ignored, and scratchpads keep
their mode while claimed. Restart adoption preserves established client identity and
dock/desktop fixture roles before observing current classification defaults. Client identity survives even
when its type now names a dock, desktop or popup. Saved representation includes modes
originally chosen by classification defaults.
It does not replay type/transient updates or matching rules over saved clients.
Current metadata still supplies effective layer/skip defaults; subsequent metadata
changes resume the ordinary live policy.

Desktop and dock windows are listed, stacked and classified, but they have no
workspace and ignore `_NET_WM_STATE`, `_NET_WM_DESKTOP`, and move/resize requests.

Initial application state precedes the first matching rule. Later supported
application requests, user actions, and rule actions replace the same field's intent.
Rules are applied actions, not persistent constraints; the configuration reference
owns [matching and reload semantics](config.toml.example). Geometry rules do not
veto subsequent ConfigureRequests. Pending scratchpad claims can respond to metadata
independently of rule changes.

Modal state projects the layer to Above; fullscreen projects it to the Fullscreen tier.
Neither erases the underlying layer preference. Leaving these states reveals that
preference again. Both atoms in one `_NET_WM_STATE` request are resolved together,
duplicate atoms apply once, and invalid action codes are ignored.


## State and visibility

The supported EWMH state surface is:

- `_NET_WM_STATE_FULLSCREEN`
- `_NET_WM_STATE_MAXIMIZED_VERT`, `_NET_WM_STATE_MAXIMIZED_HORZ`
- `_NET_WM_STATE_HIDDEN`, `_NET_WM_STATE_STICKY`
- `_NET_WM_STATE_ABOVE`, `_NET_WM_STATE_BELOW`, `_NET_WM_STATE_MODAL`
- `_NET_WM_STATE_SKIP_TASKBAR`, `_NET_WM_STATE_SKIP_PAGER`
- `_NET_WM_STATE_DEMANDS_ATTENTION`
- `_NET_WM_STATE_FOCUSED`

`FOCUSED` is WM-owned; client attempts to change it are ignored. Above and below are
mutually exclusive, modal implies above, and fullscreen supersedes maximize: entering
fullscreen clears both maximize flags, and maximize requests while fullscreen are
ignored. Leaving fullscreen restores normal geometry. Maximize changes geometry only for
floating clients. Only one visible tiled or floating fullscreen client owns a monitor at
a time: the one that most recently entered fullscreen, explicitly requested fullscreen
again, or was shown again by LWM while fullscreen. Repeated `_NET_WM_STATE` ADD
requests renew priority; duplicate fullscreen atoms within one message apply once.
Other normal clients there are suppressed except managed transient descendants of
the owner, including dialogs opened by other dialogs. A descendant still needs its
own workspace/sticky and non-iconic eligibility; an intermediate parent's placement
or hidden state does not change ancestry. Missing or unmanaged parents end a chain.
Cycles grant an exemption only when the chain reaches the owner; traversal terminates
and never rewrites the hints. Each monitor applies its own owner.
Changing `WM_TRANSIENT_FOR` or removing an intermediate parent updates descendants'
exemptions even without a workspace move. Activation uses the same exemption.
`_NET_WM_FULLSCREEN_MONITORS` changes fullscreen geometry, not ownership across
monitors. A changed topology (output names, order, or geometry), whether live or across
exec handoff, clears these index-based hints; a refresh reporting the same outputs keeps
them. Unchanged outputs preserve active drags and focus traversal. If only the root
extent changes, dock reservations are recomputed; a split drag ends only when its
workarea or other captured context changes.

LWM writes ICCCM `WM_STATE` as `NormalState`, `IconicState` for a window LWM hid,
and `WithdrawnState` on unmanage, when it also removes `_NET_WM_STATE_FOCUSED`. Other
state atoms stay in place for a later remap. A workspace change moves a client off-screen without
changing `WM_STATE`. Because LWM itself does not unmap normal managed windows, an
`UnmapNotify` is treated as client withdrawal.

Applications cannot minimize themselves. A tiling layout has no iconified place for a
window, so LWM ignores `WM_CHANGE_STATE(IconicState)`, `_NET_WM_STATE_HIDDEN` requests,
and `WM_HINTS.initial_state = IconicState`, and does not advertise
`_NET_WM_ACTION_MINIMIZE`. Only LWM hides windows, through scratchpads; it then
publishes `IconicState` and `_NET_WM_STATE_HIDDEN`, and a `MapRequest` or activation
shows the window again. Adoption after restart restores the hidden state a predecessor
published. Showing the desktop (`_NET_SHOWING_DESKTOP`) is not supported.

Fullscreen geometry is applied before the first map. Initial maximize is also resolved
before mapping; only floating geometry changes.

## Focus and activation

LWM reads `WM_HINTS.input`, urgency, `WM_TAKE_FOCUS`, `_NET_WM_USER_TIME`, and
`_NET_WM_USER_TIME_WINDOW`. A client is focus-eligible when input is accepted or
`WM_TAKE_FOCUS` is advertised. Missing `WM_HINTS.input` means true. On focus, LWM sends
`WM_TAKE_FOCUS` when supported and also sets X input focus directly. Runtime changes to
`WM_HINTS`, `WM_PROTOCOLS`, and user-time properties are honored. Focus that LWM moves
on its own, after the active window closes or becomes ineligible, does not count as user
interaction with the replacement.

Application and WM-initiated urgency are tracked separately and their combined state
is published in both `WM_HINTS` and `_NET_WM_STATE_DEMANDS_ATTENTION`. Clearing the
urgency hint or deleting `WM_HINTS` withdraws the application's request; any outstanding
WM-initiated request survives and restores the hint. Focusing the window clears both
sources. Urgency hints set on an already-active window are cleared.

For `_NET_ACTIVE_WINDOW`, when another client is active, source `1` application requests
require a nonzero timestamp that is not older than the active client's known user time.
Rejected application requests set `DEMANDS_ATTENTION`. Source `2` pager/user requests
are accepted when the target is otherwise eligible. No request surfaces a window
suppressed by a current fullscreen owner.

## Client messages and geometry

LWM handles:

- `_NET_CURRENT_DESKTOP`, `_NET_WM_DESKTOP`
- `_NET_ACTIVE_WINDOW`, `_NET_CLOSE_WINDOW`
- `_NET_WM_STATE`
- `_NET_MOVERESIZE_WINDOW`, `_NET_WM_MOVERESIZE`
- `_NET_RESTACK_WINDOW`
- `_NET_REQUEST_FRAME_EXTENTS`
- `_NET_WM_FULLSCREEN_MONITORS`

Desktop indices outside the current monitor/workspace graph are ignored. A missing or
sticky desktop hint at initial manage means the focused monitor's current workspace.
A transient with a managed parent joins the parent's workspace when it is first
managed and whenever `WM_TRANSIENT_FOR` later names a parent, in either mode; a
floating transient is centered on the parent unless an accepted position hint places it.
Startup resolves all newcomer placements and rules before centering on the completed
scene, regardless of scan order or a parent's mode. Surviving clients use saved intent;
only newcomers receive initial placement during restart adoption.

LWM places frames: a client's X window together with its border. Padding surrounds
tile frames, maximize fills the workarea with the frame, and centering, clamping and
monitor selection use frames; fullscreen windows have no border. Geometry that
applications and rules supply (ConfigureRequest, `_NET_MOVERESIZE_WINDOW`,
`WM_NORMAL_HINTS` sizes, rule `geometry`) names the window inside the frame. A changed
border width keeps the frame and resizes the window. The effective border is limited
to the largest width that leaves at least one interior pixel in both dimensions;
small frames reduce the border, and fullscreen has none. Window size requests retain
omitted inner extents; unchanged sizes and position-only requests keep the frame.
Frames saturate at 65535, including both borders, so the maximum effective border is
32767. Empty frame extents in a restart snapshot are rejected.

Tiled clients keep layout-owned geometry and receive synthetic `ConfigureNotify`
replies. ConfigureRequests for tiled and floating clients receive one synthetic
acknowledgement per processed request, even when the resulting rectangle is unchanged.
Hidden tiles report their [derived normal slot](ARCHITECTURE.md#placement-and-geometry),
which is also the rectangle used when their workspace is shown.
Normal server-generated ConfigureNotify events may also occur when geometry changes.
Floating configure and moveresize requests are constrained by WM policy; moving a
floating window can reassign its monitor. Floating moveresize requests and pointer drags
saturate dimensions to 1..65535 and coordinates to the signed 16-bit range instead of
wrapping. Changing a client from tiled to floating restores its saved floating
rectangle, or its current tiled rectangle if none was saved; a rectangle lying entirely
outside the monitor's workarea is centered on it instead. Fullscreen, maximized, and
workspace-hidden presentation do not replace that normal rectangle.

Managed tiled/floating restack requests reapply LWM's global stacking policy. Requests
for unmanaged, desktop, and dock windows are forwarded, after which LWM reasserts
managed ordering.

LWM reads initial and runtime `WM_NORMAL_HINTS` position and size hints for floating
clients. An unanchored position chooses the monitor containing the hinted center. A
transient or EWMH-desktop anchor constrains the target monitor; an invalid hint falls
back to LWM placement. Minimum size, resize increments, aspect ratio, and gravity are
not enforced. Positive size hints above 65535 saturate to the X11 extent limit;
nonpositive size hints retain the existing size. Hints update the normal floating
rectangle even while maximized or fullscreen; presentation remains governed by those
states until they are cleared. A pointer move/resize exits maximize using the currently
displayed rectangle as the starting geometry. Fullscreen windows cannot be interactively
dragged. `_NET_WM_MOVERESIZE` supports pointer movement and all eight resize directions
as defined by [EWMH](https://specifications.freedesktop.org/wm/latest/ar01s04.html).
Resizing fixes the opposite edge while bounding coordinates and extents. The specified
initiating button ends the interaction; zero accepts any release. A cancel request only
ends an interaction for the same window, preserving the last applied floating rectangle.
Keyboard move/resize requests and interactive requests to start dragging tiled clients
remain unsupported. User mouse bindings can move tiles and resize their splits; resizing
a tile away from a split turns it into a floating client. Losing the dragged client's
eligibility releases the pointer without waiting for another motion or release.

Coordinates saturate to the signed 16-bit range before placement policy is applied.
Oversized dock struts cannot wrap workarea arithmetic.

`_NET_WM_STRUT_PARTIAL` reserves root-relative edge regions with inclusive coordinate
ranges, as specified by
[EWMH](https://specifications.freedesktop.org/wm/latest/ar01s05.html). Each region is
projected onto every intersecting monitor, independently of the dock window's position.
Workareas remain rectangular: an intersecting partial range reserves the corresponding
monitor edge. Overlapping reservations use the largest inset, not their sum. Inverted
ranges reserve nothing on that edge. A complete, correctly typed partial property takes
precedence over `_NET_WM_STRUT`, including when all extents are zero. Missing or
malformed partial data falls back to the four-value legacy property, whose ranges span
the root edges. Frame extents are always zero because LWM does not create decorations.

Scalar window/time hints require a complete, correctly typed 32-bit value; malformed or
truncated hints use the same fallback as absent hints. Window titles require 8-bit text
and retain a bounded 4 KiB prefix. If `_NET_WM_NAME` is absent, empty, or has the wrong
type or format, LWM tries `WM_NAME`, then `Unnamed`.

## WM protocols

`_NET_CLOSE_WINDOW` applies only to managed clients, docks and desktops; requests
naming any other window, including LWM's own, are ignored.
Closing a window (`window close` or `_NET_CLOSE_WINDOW`) sends `WM_DELETE_WINDOW`,
and `_NET_WM_PING` when the client supports it. Only an unanswered ping proves a client
hung: a ping-capable client that does not answer within five seconds is killed. Any
other client may be showing a confirmation dialog and is killed only if the window is
closed again while it is still open. A client without `WM_DELETE_WINDOW` is killed
immediately.

## Per-window and private properties

For managed windows LWM maintains `_NET_WM_DESKTOP`, `_NET_WM_STATE`,
`_NET_WM_ALLOWED_ACTIONS`, and zero `_NET_FRAME_EXTENTS`. Move and resize are advertised
only for floating clients.

`_LWM_WINDOW_CLASS` is a stable LWM extension containing the UTF-8 value `tiled`,
`floating`, `dock`, or `desktop`. Compositors and other local tools can use it when
`_NET_WM_WINDOW_TYPE` does not distinguish tiled and user-floated windows.

LWM's `WM_S0` owner window, which is also the `_NET_SUPPORTING_WM_CHECK` window,
carries the IPC state in `_LWM_STATE` and accepts `_LWM_COMMAND` requests; replies use
`_LWM_REPLY` on the caller's window. [IPC.md](IPC.md#transport) defines the protocol.

`_LWM_RESTART` and `_LWM_RESTART_OWNER` are temporary exec-handoff records on the
root window, not a public API. Clients should neither interpret nor modify them. Their
ownership and version rules are described in [ARCHITECTURE.md](ARCHITECTURE.md#restart-and-process-lifetime).

## Intentional limits

LWM does not implement window shading, virtual roots, icon publication, visible-name
properties, `WM_COLORMAP_WINDOWS`, session-management protocols, or system-tray
ownership. Popup-only windows are not integrated into workspace, focus, or stacking
policy. LWM is not a compositor.
